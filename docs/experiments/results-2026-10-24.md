## Findings: bugs the live runs exposed, all fixed test-first before the counted run

1. **The MQTT config flow (Home Assistant 2026.10)** requires an `other_settings` section in the broker step. VESPER's fake Home Assistant had accepted the old payload. Fixed in ff28f8f.
2. **Onboarding token persistence.** Home Assistant was stopped seconds after onboarding, before its delayed auth-store write, so the next run's saved credentials were refused. Onboarding now ends only once the token is on disk. Fixed in 96f84be.
3. **Numeric select options.** Home Assistant's select sends options as strings ("38400"), and the twin rejected them for a numeric enum (`zigbee:nous:d4z-m`, `rs485_baud_rate`). Fixed in fc24463.
4. **Crosswalk device classes and units.** 9 VOC sensors reporting in ppb/ppm had been given `volatile_organic_compounds`, which Home Assistant allows only in µg/m³ or mg/m³. 2 illuminance sensors reporting in % had been given `illuminance`, which requires lx. They now get `volatile_organic_compounds_parts` or no class. Fixed in bb0f2b0, which accounts for the first discovery run's 11 rejections.
5. **A stale catalog.** The catalog built on 10-22 predated a units fix (b624d8d). It is now refused by every command that runs twins (52af5cb), and the slot rebuilt it first.

The failed attempts are kept beside the counted runs: `acceptance-20261024T151448Z.json` (94/95, before fix 3) and the `acceptance-run*.log` files.

## E2: real devices (fails as pre-registered)

**Data.**
- ZIOTP2025 at commit c3481e8 (clean checkout): 91 Zigbee captures from two topologies, captured 2023-10-12 to 2023-11-28.
- Decryption is MIC-verified, with a minimum rate of 99.92% per file. Set aside: 1,940 secured frames of other PANs, 253 undecodable and 394 manufacturer-specific reports.
- Reports from two addresses not in the dataset's device list were counted and not used: 48 from A:0x4a30 and 249 from B:0xb1bf.

**Streams.** 23 streams are eligible (≥ 20 informative intervals). 4 of them are firmware-governed Aqara streams, reported but not judged, so 19 are judged.

| Device (topology:name@address) | Attribute | Informative intervals matched | Verdict |
|---|---|---|---|
| A:Ledvance RGBW Bulb@0x054f | level (0x0008/0x0000) | 87/89 (97.8%) | pass |
| B:Ledvance Bulb@0xec7f | level | 62/62 (100%) | pass |
| B:Philips Motion (SML001)@0x059b, endpoint 2 | illuminance (0x0400/0x0000) | 80/82 (97.6%) | pass |
| A and B "Smart Socket" (Tuya), B "Power Plug" ×2 (Senckit) | metering summation, rms voltage and current, active power, on/off: 16 streams | 0–25% | fail |

**Reading.** The 16 failing streams share the device-side signature named in the pre-registration:
- almost every interval is `steady` with a median near 300 s, against ZHA's configured maximum of 900 s (heartbeat ratio about 0.33);
- every disagreement is `missed`: the device reported before the rule says it would.

The generic plugs' firmware sends its own periodic reports and ignores the configured maximum interval.

**The rule was checked.** The capture dates lie outside the window over which the rule table was verified, and the result flags this. Afterwards, Home Assistant core 2023.10.0 and 2023.11.0 (`homeassistant/components/zha/core/const.py` and its cluster handlers) were checked: they use the same constants (maximum interval 900 s, minimum 30 s, OP minimum 5 s) and the same configuration for every failing attribute. So the rule is not the cause.

**What the paper may claim.**
- VESPER's reporting runtime matches real devices whose firmware follows the hub's reporting configuration: 3 streams, 98–100% of informative intervals.
- The test does not support "VESPER reproduces real devices" in general.
- Generic plugs ignore the configured maximum interval; this is itself a finding about device diversity.

**A possible exploratory follow-up**, labelled exploratory: read the captured ZCL Configure Reporting responses, to show per device whether it accepted ZHA's configuration.
